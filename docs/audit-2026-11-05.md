# Spawn audit — 2026-11-05

Scope: the whole repository at commit `91f4197` — all five crates, `scripts/rsi/gate.sh`, the SQL schema, and `web/`.

Method: seven subsystem reviewers read their code completely, every candidate finding was then checked by two independent skeptics (one trying to refute it from the code, one checking reachability and blast radius in the real deployment). A finding is listed only when both confirmed it. Four were also reproduced empirically (marked **reproduced**). A completeness pass found nothing further.

Results: **5 high, 16 medium, 11 low**. Three candidate findings were dropped as false positives during verification (see [Refuted](#refuted)). `cargo clippy --workspace --all-targets` is clean and the host-side unit tests pass; the `spawn-postgres` integration tests need `SPAWN_TEST_DATABASE_URL` and were not run (they fail closed rather than skip).

Line numbers anchor the commit above.

## High

### H1. Model-switch Stop marks the task delivered; the worker is never resumed and the task is lost

`crates/spawn-cli/src/deliver.rs:291`

When a live idle worker's model profile differs from the task's, `delivery()` returns a `Stop` order keyed `switch-model-<task>-<revision>`. The comment says the next pass resumes the stopped worker on the task's models, but this Stop is built with `task.order(...)` (`task: Some(self.id)`, `deliver.rs:97`), so `dispatch::submit` immediately records the delivery (`dispatch.rs:307` → `spawn_task_delivered` flips assigned/revise → delivered, `schema.sql:1152`). The Bridge then kills the engine, and the task is stuck in `delivered`: the resume branch only matches `Assigned | Revise`, the liveness rule treats `stop` as intentional (`supervise.rs:64`), and no escalation is raised. The prompt is never sent and no report can ever be written.

Trigger is the documented per-task `--model cheap` feature, not an edge case. Recovery needs a human to cancel/reassign and restart the resident.

Fix: issue the switch-model Stop without the task link (an `Order` with `task: None`, or skip `task_delivered` when the action is Stop), so the task stays assigned/revise and the next pass resumes it with the normal `deliver-<id>-<rev>` key.

### H2. Screen parser: any body line can fake a permission dialog

`crates/spawn-core/src/screen.rs:169` — **reproduced**

`permission_line` treats any line in the 14-line body above the prompt as a live dialog: a `Do you want to` / `Would you like to` prefix, or a numbered line containing `. Yes` (`screen.rs:164-172`). The body includes captured command stdout and model prose; it is not engine UI. An idle pane ending in installer output `Do you want to continue? [Y/n]`, or model text `1. Yes, delete it and continue`, reads `ScreenState::Permission`.

Consequences: the Observer writes a rules-tier BLOCKED that pages a human (`classify.rs:52`), and every queued input is rejected with "does not accept input" until more than 14 lines scroll the text away. An LLM can trigger this from its own output with no dialog present.

Fix: match the engine's real dialog shape (a numbered `<n>. Yes` paired with `<n>. No`, or the prompt-body choice the parser already handles at `screen.rs:262`), and/or anchor the phrase to the input region of the screen-reader layout.

### H3. Screen parser: any body line starting with "Error" wedges resume and input

`crates/spawn-core/src/screen.rs:204` — **reproduced**

`error_line` matches any body line starting with `Error` that also contains "error"/"Error"; only the exact `Error: Exit code` shape is carved out. Capitalized `Error: …` lines are normal in compiler, test, stack-trace and log output. A pane ending in `Error: connection refused, retrying` reads `ScreenState::Error`; `type_prompt` then waits 10 s for Ready and fails the whole start/resume without typing the prompt (`bridge.rs:1472-1522`), queued inputs are rejected, and the Observer keeps consulting the judge about an "engine error" that is only quoted output.

Fix: infer engine errors only from engine-drawn shapes (the `API Error` status line and the `tool error:`/`Error: Exit code` pair), and use the transcript's `TurnFailed` for the fact; at minimum require the line in the input/status region, not anywhere in the body.

### H4. Chunking follows symlinks and blocks on agent-planted FIFOs

`crates/spawn-host/src/chunks.rs:548`

`store_file` opens an agent-written large file with a plain `File::open` — no `O_NOFOLLOW`, no `O_NONBLOCK`. The only check is a `symlink_metadata().is_file()` in `store_large` (`git.rs:451`), a separate syscall, so the engine can swap the path between the stat and the open.

- Symlink swap: replace a 9 MiB tracked file with a symlink to a host file the controller uid can read (`~/.ssh/...`, the owner's `spawn.env`) during the stat/open window; the host bytes are compressed into the chunk store and named in the checkpoint manifest, then written back as a normal file inside the workspace on the next mount — host content the engine could not read from its container.
- FIFO swap: replace the file with a FIFO that has no writer; `File::open` blocks the tick indefinitely.

This contradicts the documented guarantee that agent-written files are opened without following symlinks and a planted FIFO cannot stall the host (the hardened opener exists already as `read_local` in `tmux.rs`).

Fix: open with `O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, `fstat` the descriptor, require `S_ISREG`, bound the read; drop the file from the manifest (or fail the checkpoint) when the descriptor's stat differs from the earlier lstat.

### H5. Mission source URLs reach controller-side git with no protocol allowlist

`crates/spawn-cli/src/sources.rs:206` (with `schema.sql:1056`) — **partially reproduced**

A mission's `source` is documented as "any git repository (a path or URL)" (`docs/fleet-architecture.md:288`). `spawn_mission_add` stores it verbatim, and the only CLI check is that it does not start with `-` (`sources.rs:206`). The same string is then handed to `git clone --bare -- <source>` (`sources.rs:213`), `git fetch -- <source>` (`sources.rs:244`) and `git push -- <source> <refspec>` (`push.rs:48`) — all run by the controller, outside the gate's bwrap sandbox, with the controller's full environment and no `GIT_ALLOW_PROTOCOL` set anywhere.

The privilege path matters: the `spawn_supervisor` DB role — the LLM supervisor — is granted `spawn_mission_add` (`schema.sql:1488-1495`), and its charter tells it to add missions it hears about in its pane. Worker reports are typed into that pane, so prompt injection crosses from an engine into the choice of source. The clone runs the first time the integrator touches the mission (`integrate.rs:374`) or a worker starts.

On unpatched git within the version range the README declares (`git 2.30 or later`), `protocol.ext.allow` defaulted to `user`, so a source of the form `ext::sh -c <command>` executes an arbitrary command on the controller host at clone/fetch time (the CVE-2022-39253 fix only reached this default in 2.30.6 / 2.34.8 / 2.38.1; Ubuntu 22.04 shipped 2.34.1). On this machine's git 2.50 the bare URL is refused by default, but I confirmed the command executes under `-c protocol.ext.allow=user` — i.e. Spawn adds no defense of its own and safety depends entirely on the deployed git build and the host's git config.

Fix: allowlist the URL schemes Spawn accepts (absolute path, `https://`, `ssh://`), reject `ext::` explicitly, run every controller git invocation with a pinned `GIT_ALLOW_PROTOCOL`, and restrict setting a non-path source to the owner (the supervisor need only add sourceless or controller-configured missions).

## Medium

### M1. Worker report text can forge digest markers and suppress future escalations

`crates/spawn-cli/src/dispatch/digest.rs:30` — **reproduced** (temporary test against the real `told()`)

`told()` substring-scans succeeded digest commands for `[spawn:esc …]` markers, but digest lines embed untrusted worker report text (`deliver.rs:480`). A report containing `[spawn:esc missions mission-5]` is indistinguishable from the marker the dispatcher appends; that escalation is then filtered on every future tick. A worker can pre-suppress future mission news, human messages, other reports, and delivery-failure alerts by guessing the sequential ids (`mission-<n>`, `report-<task>-<rev>`, …).

Fix: recognize only a marker at the fixed end-of-line position (strip `]`, take the final bracketed token), or delimit the payload so embedded text cannot match.

### M2. `spawn serve` is single-threaded and has no timeouts

`crates/spawn-cli/src/serve.rs:70`

One synchronous accept loop; every handler opens a fresh PostgreSQL connection and `/api/pane/<id>` runs `tmux capture-pane` (or `docker exec`) inline, all without timeouts. A client that reads one byte then stops draining blocks `respond()` forever; a hung docker daemon stalls the pane endpoint — either freezes the API for every client, repeatable with a handful of connections.

Fix: a bounded thread pool (or per-request threads with a semaphore), server read/write timeouts, a timeout around the tmux/docker call.

### M3. Default token-free loopback serve has no Host/Origin check

`crates/spawn-cli/src/serve.rs:157`

With the default `127.0.0.1` bind and no token, every API request from a loopback source is answered, and Host/Origin are never inspected. A malicious web page can use DNS rebinding (its hostname resolves to 127.0.0.1 after the browser pins the origin) to read `/api/overview`, `/api/missions` and live pane JSON with no token.

Fix: require Host to be `127.0.0.1`/`localhost`/`[::1]`, or require a token for JSON even on loopback.

### M4. Main can merge into a workspace while a turn is starting

`crates/spawn-core/src/bridge.rs:665`

`idle_merge_due` gates only on the last *confirmed* screen state. A fresh contradicting frame (Busy) is stored in `follow.seen` but, on first reading, neither recorded nor applied to `follow.screen` (`bridge.rs:903-907`), so the last confirmed Ready still authorizes the merge one tick after a prompt started. After a Bridge restart the window is wider: `merge_at` resets (merge offered immediately) and the optimistic in-memory `turn_open` is gone, while `follow.screen` folds to the Ready frame recorded before submit. Main's files — or conflict markers — are then written under a running turn, breaking the documented invariant at `bridge.rs:183`. **Reproduced** by the verifier with throwaway tests.

Fix: require the just-read frame to agree (two agreeing Ready frames after restart) before merging, and persist the optimistic turn-open as a keyed event.

### M5. A database error while typing the start prompt leaves a live, promptless engine

`crates/spawn-core/src/bridge.rs:1269`

`start()` maps an `Outcome::Failed` from `type_prompt` to `abandon()`, but the `?` at line 1269 also propagates a `StoreError` (the ready-screen append at `bridge.rs:1501` can fail on a transient DB error) *before* `submit_text`. The tick returns before `queue.finish`; after the 2-minute lease another attempt folds `ExecutionStarted` and fails with "already runs an execution", the original command finishes Failed, and the engine sits at an empty prompt forever — the liveness rule sees a live session and never revives it.

Fix: run the same abandon path on `StoreError` from `type_prompt`, or make the ready-screen append best-effort; alternatively let the retried Start re-type when the active engine has no delivered prompt.

### M6. An Input command whose lease expires is typed twice

`crates/spawn-core/src/bridge.rs:1562`

Start is fenced against re-execution by the folded view; Input is not. `submit_text` runs on every claim attempt, and the `cmd_<id>:notice` key only dedupes the log event, not the keystrokes. The tmux calls have no timeout; a stall past the 2-minute lease (wedged docker daemon, tick killed after paste) lets another tick claim attempt 2 and send the same prompt again — the engine performs non-idempotent actions twice.

Fix: a log-derived effect fence for input (keyed `cmd_<id>:submitted` after a successful paste), and timeouts on the host calls.

### M7. Crash between unmount and `execution.ended` wedges the execution permanently

`crates/spawn-core/src/bridge.rs:1007`

`end()` commits, terminates, and unmounts first, and only then appends the keyed `ExecutionEnded` (`bridge.rs:1012`). If the process dies or the append fails in that window, recovery rebuilds the execution as active and re-enters `end()` forever: the final `commit` runs against the now-deleted directory, fails, climbs to `ExecutionEndStalled`, and every Start/Resume — including liveness revival — is rejected with "already runs an execution". Only a human `discard` clears it. No data is lost (the final commit succeeded), but the log-only-state claim does not reconcile this ordering. **Reproduced** by the verifier.

Fix: treat a commit against an already-absent workspace as `Commit::Unchanged` (the final commit pre-dates the unmount), or append `ExecutionEnded` independently and reconcile a missing directory as the desired end state.

### M8. `utc_ms` panics on integer overflow from an engine-writable timestamp

`crates/spawn-core/src/ingest.rs:101` — **reproduced**

Year/hour/minute/second parse as unrestricted `i64`; only month/day are range-checked. A transcript timestamp like `99999999999999999-11-04T05:46:12.000Z` overflows the Hinnant arithmetic (debug panic confirmed at line 101; release wraps silently). The bytes come from the engine-writable Claude transcript. Because the read offset is in-memory, a debug wedge restarts and re-panics on the same line, permanently wedging the worker's tick.

Fix: validate ranges (year 1..=9999, hour 0..=23, …), compute with checked arithmetic/`i128`, return `None` on overflow — the caller already treats an unreadable time as "keep the line".

### M9. A forged transcript line closes the turn and triggers a mid-turn merge of main

`crates/spawn-core/src/ingest.rs:151`

Any non-meta user line beginning `[Request interrupted` maps to `TurnStopped`, and Codex's writable JSONL gets the same treatment for `turn.completed`. The post-`TurnStopped` auto-merge (`bridge.rs:652`) requires no Ready-screen corroboration. Both files are writable by the engine, so an agent can append the line while its turn runs; the next tick records turn stopped, checkpoints, and merges main into the live workspace — mutating files, inserting conflict markers, and injecting the merge notice into the next prompt.

Fix: require a confirmed Ready screen before that merge (as `idle_merge_due` already does), and treat transcript turn markers as hints pending a corroborating channel.

### M10. Busy markers in model/command output fake ScreenState::Busy

`crates/spawn-core/src/screen.rs:182`

A body line containing `esc to interrupt`, `Running…`, `Nucleating…`, `(ctrl+b ctrl+b`, or starting with a spinner glyph plus `…`/` for ` reads as Busy. Build progress output, a README, or a deliberately printed fake spinner in the tail of an idle pane pins Busy indefinitely: inputs refused, rules-tier WORKING with no model consult, supervisor waits forever.

Fix: accept busy markers only at the engine-owned status position, not as body substrings.

### M11. Redrawn history fakes the workspace-trust dialog and injects `y`/Enter

`crates/spawn-core/src/screen.rs:221` — **reproduced**

`is_trust_dialog` is true when the tail merely *contains* `Yes, I trust this folder` and no prompt marker is present. On resume, Claude redraws prior output before the input box; a line the agent catted earlier (this repository's own `screen.rs` contains the string) is enough for the Bridge to send literal `y`, `Enter` keys, which land in whatever is focused. The one-shot `trusted` flag does not help because the detection itself is false.

Fix: match the full ordered dialog block at the top of a fresh pane, require it to persist across two reads, and never send keys on a single frame during a resume redraw.

### M12. Chunk-store materialize falls back to lexical paths without /proc

`crates/spawn-host/src/chunks.rs:591`

`Held::entry` routes through `/proc/self/fd/<n>` only when /proc exists; on macOS/BSD it joins lexical paths. O_NOFOLLOW opens of each component do not protect the final create/rename from a directory-swap after the open, so a surviving background process looping a directory→symlink swap can get `materialize` to write chunk bytes to an arbitrary host path. Linux deployments with /proc are immune; the dev host (darwin) is not.

Fix: use `openat`/`mkdirat`/`renameat` relative to the held fd on non-/proc targets, or refuse materialize when /proc is unavailable.

### M13. gc can delete chunks a concurrent checkpoint has written but not committed

`crates/spawn-host/src/gc.rs:133`

Liveness is computed from commits existing at scan time; chunks are written before the commit that names them. A checkpoint longer than the default 60-minute grace (large working set, slow disk) racing an hourly gc loses its early chunks; the commit then publishes a manifest naming missing objects, and every future mount fails with `ChunkError::Missing`, unrecoverable for data deliberately kept out of git. A narrower stat/unlink TOCTOU in `remove_if_older` has the same effect.

Fix: coordinate with the checkpoint lock (the existing branch `spawn-lock` or a global gc lock around `store_large`), unlink through the same fd whose mtime was checked, and set the default grace above any plausible checkpoint duration.

### M14. `unresolved()` blocks forever on a FIFO at a conflicted path

`crates/spawn-host/src/git.rs:1347`

Deciding whether conflict markers remain uses `std::fs::read` on agent-controlled paths — follows symlinks and blocks on opening a FIFO with no writer. It runs on every merge with a pending conflict and every later checkpoint, holding the branch lock; one `mkfifo` stalls that agent's checkpoints and merges indefinitely and cascades lease retries.

Fix: use the hardened `O_NOFOLLOW | O_NONBLOCK` + regular-file opener from `tmux.rs`.

### M15. Supervisor revival counts failed commands, not failed revivals — a crash-looping engine restarts forever

`crates/spawn-postgres/src/sessions.rs:73`

The `failures` count only counts *commands* that failed after the last execution started. A resume command succeeds as soon as the engine launches; the engine dying `lost` seconds later is a new end, not a failed command, so the counter stays 0 forever. The designed backoff and "three failures then start fresh with handoff" path never engages: a native session that crashes on attach (segfault, OOM, corrupt state) is relaunched in a tight storm that burns API tokens, and the same storm on an ephemeral worker never escalates.

Fix: count revival outcomes (an execution ending `lost` within a grace window after a liveness resume) rather than failed command rows.

### M16. Gate: protected paths can be moved out of their prefix with a rename

`scripts/rsi/gate.sh:419` — **reproduced**

The guard lists changes with plain `git diff --name-only`, which performs rename detection and prints a rename as one line naming only the destination. I verified: `git mv rsi/scenarios/001.sh weaken.sh` makes `--name-only` print only `weaken.sh`, while `--no-renames` prints both paths. A candidate can `git mv scripts/rsi/gate.sh gate-old.sh` (or move a scenario/blackbox helper out), weaken the moved file, and pass the guard; the controller's own checkout still runs current scenarios, so the gate accepts and lands the weakening, which takes effect on the next controller deploy.

Fix: build `changed` with `git diff --name-only --no-renames -z` (or `--name-status -z` and cover both rename endpoints).

## Refuted

Three candidates did not survive verification and are not issues:

- `schema.sql:1440` "legacy import skipped for a residents-only database" — inverted reading of the guard's boolean logic.
- `spawn-postgres/src/lib.rs:141` "url_password parses the port as the password" — misread `Option::and_then` chaining.
- `observer.rs:472` "a model-printed `HUMAN:` line forces attention" — intended, documented, and test-pinned behavior (the designed human-question channel).

## Verification notes

- `cargo clippy --workspace --all-targets`: clean.
- Host-side `cargo test --workspace`: pass. The `spawn-postgres` integration suite requires `SPAWN_TEST_DATABASE_URL` against a disposable PostgreSQL (it fails closed rather than skipping) and was not executed in this environment, which has no local PostgreSQL or Docker.
- The codebase's baseline defenses were reviewed and found sound across the trust boundaries: queue leasing uses `FOR UPDATE SKIP LOCKED` with attempt fencing; all SQL is parameterized; shell argv is passed without a shell and `shell_quote` is injective; workspace ids and agent/session/branch identifiers are charset-validated; chunk materialize validates manifests and paths; static serving canonicalizes and rejects `..`; the serve token comparison is constant-time; the web UI has no `dangerouslySetInnerHTML` and its markdown renderer builds React elements only. The findings above are the gaps in that model, most of them about trusting *engine output* (screen text, transcript files, reports) at the same authority as engine UI or controller-generated markers.
